# 文化体系の利用過程を追跡する

- Status: Research observation template / no runtime rule change
- Date: 2026-08-30
- Related: `framework-loading-depth-observation.md`, `kj-atlas-case001-longitudinal-companion.md`, `v39-deepseek-api-validation.md`

## 目的

文化体系について、**候補に上がったこと、資料を読んだこと、体系固有の操作を行ったこと、対象側の成果へ採用されたこと**を分けて記録する。

これらをすべて「frameworkを使った」とまとめると、次の違いが見えなくなる。

- 候補には上がったが、不採用条件に当てはまり、読む前に棄却した。
- 詳細まで読んだが、対象側の増分がなく、操作は行わなかった。
- 操作を試したものの、forcingや不適合を検出し、対象側へは採用しなかった。
- 文化体系から生じた問いが、後の資料によって対象側の所見として残った。

この記録は実行手順ではない。`candidate → loaded → operated → adopted`を順番に必ず進めるものではなく、**実際に何が起きたのかを後から取り違えないための来歴記録**である。

## 記録単位

一つの文化体系候補について、観察上意味がある場合だけ、一行または短いブロックを残す。候補を網羅的に列挙することは目的にしない。

### `candidate`

その体系が候補に上がった理由を、対象側の言葉で残す。

- 対象のどの問い、空白、関係に反応したか。
- 利用者から明示的に指定されたのか、探索中に自然に候補となったのか。
- どの条件なら不採用とするか。

候補に上がっただけなら、ここで止めてよい。

### `loaded`

実際に作業コンテキストへ入れた範囲を残す。

- `none`
- `selection_only`
- `application_rule`
- `framework_detail`
- `multiple_frameworks`

可能であれば、参照した資料、ファイル、外部sourceも記録する。読み込み範囲の定義は`framework-loading-depth-observation.md`に従う。

### `operated`

体系固有の操作を実際に行ったかを残す。

- `none`
- 操作名または短い説明。
- 何を対象材料として操作したか。
- 途中で止めた場合は、その理由。

資料を読んだだけなら`none`でよい。操作しなかったことを欠落とはみなさない。

### `adopted`

文化体系を外した後にも対象側へ残ったものだけを記録する。

例:

- 新しい問い。
- 新しい調査先。
- 関係候補。
- 反証条件。
- KJ再編。
- 設計、文章、判断への実際の採用。

何も残らなければ`none`とする。文化体系内部の説明が増えただけなら、採用には数えない。

### `stop_reason`

それ以上深めなかった理由、または採用しなかった理由を短く残す。

例:

- 不採用条件に該当した。
- 同種性を確保できなかった。
- baselineとの差がなかった。
- 詳細まで読んだ後に、文化体系の語彙だけが増えた。
- forcing / provenance loss / target distortionを検出した。
- 現在の問いには浅い利用で十分だった。

## 短い記録例

```text
framework: 五行
candidate: 自己改善loopの「促進」と「抑制」を別の関係動詞で見る候補として浮上
loaded: selection_only
operated: none
adopted: feedback loopの抑制側を確認する調査問い
stop_reason: 分類器としての同種性がないため詳細対応へ進まない
```

```text
framework: 易
candidate: 状態遷移の不在を検査できる可能性
loaded: application_rule
operated: none
adopted: none
stop_reason: 独立した割当規約を用意できず、遷移試行へ進めない
```

## 長期ラウンドでの読み方

この記録を、その場の成功率へ集計しない。

後のラウンドでは、たとえば次を確認する。

- `candidate`だけ残した問いが、後の資料で再び意味を持ったか。
- `loaded`を深くしたことで、anchoringが長く残らなかったか。
- `operated`した内容のうち、対象へ戻した後にも何が残ったか。
- `adopted`した所見が実成果へ移ったか、その後に撤回または再編されたか。
- `stop_reason`が別ケースでも繰り返し現れ、routingの改善に使えるか。

## KJ Atlas Case 001での扱い

独立A〜D比較のarmや処置を増やさない。

B/Dで文化体系を扱った場合、必要に応じてこの記録を**実験者側の補助来歴**として残す。blind reviewerには、armや文化体系を推測できる情報を渡さない。

Case 001の独立B/Dは、事前登録済みのskill snapshotへ固定されている。新しいCSW文書やこの記録様式をarmのmodel/operator inputへ追加しない。**run出力と既存run recordを固定した後に、すでに残っている記録から実験者が補助記録を作る。** そのために追加質問、追加の文化体系探索、再実行を行わない。現在の方法論改善が、凍結済みの比較条件へ逆流することを防ぐためである。

長期companion laneでは、`framework_use`だけでは区別が足りない重要ラウンドに限って、この来歴を添える。こちらは独立A〜Dとは別のprospective観察であり、使用した`method_ref`も記録する。

## 方法論正本へ昇格させる条件

この記録様式自体は研究用であり、`src/<locale>/`のruntime規則ではない。

複数の異なる実課題で、たとえば次のような所見が繰り返し現れた場合にだけ、最小限のruntime変更を検討する。

- 候補に上げるだけで十分な問いが繰り返し得られる。
- 詳細まで読んだ後のanchoringが繰り返し問題になる。
- 体系固有の操作を省いた方が、対象固有性を保てる。
- 特定の`stop_reason`が再現し、現行routingだけでは防げない。

## 現時点の判定

現段階で必要なのは、文化体系の利用を新しい固定階層へ変えることではない。

> **候補化、読み込み、操作、採用を分けて観察し、どの段階で有用な増分が生まれ、どこでforcingやanchoringが起きたのかを長期的に追えるようにする。**

この区別を保ったまま実データを蓄積し、規則化はその後に判断する。
