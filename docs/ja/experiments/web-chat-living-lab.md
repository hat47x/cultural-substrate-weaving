# Web Chat Living Lab

## 位置づけ

この仕組みは、APIで大量の固定ケースを回すベンチマークではない。ChatGPTなどのWebチャット上で実際の執筆、調査、設計、分析を進めながら、cultural-substrate-weaving（CSW）が仕事の流れにどのような差を生むのかを、必要な範囲だけ記録するための運用観測系である。

目的は、方法を高得点に見せることではない。後から次を確かめられる状態を作ることにある。

- どの問いが変わったか。
- 新しく何を探すようになったか。
- KJのまとまりや空白が、後から組み替わったか。
- 実際の成果物や判断へ何が残ったか。
- どの操作は使わない方がよかったか。
- その場では意味が分からなかった残差が、後から意味を持ったか。

そのため、文化体系を使った数、全文を読んだ回数、体系固有の操作を行った回数、event件数はKPIにしない。

## 二つの運用モード

### `natural_work`

通常はこちらを使う。現実の仕事を止めず、自然な流れの中でCSWを使う。

一つのラウンドで行うことは、おおむね次の範囲でよい。

1. 新しい資料、観察、反証、実行結果など、今回増えた材料を見る。
2. その材料が以前の残差や孤立カードへ触れた場合に限り、必要な部分を再び前景へ戻す。
3. KJと文化体系を、現在の問いに必要な範囲だけ使う。
4. 成果物、判断、調査方針など、実作業側へ何が残ったかを見る。
5. 未解決事項と、再び開く条件を残して区切る。
6. 後から意味を持ちそうな変化が実際に起きた場合だけ、eventを記録する。

毎回、過去の履歴をすべて読み直したり、記録欄をすべて埋めたりする必要はない。

### `paired_check`

方法変更を判断するために、もう少し比較可能性を高めたい場合だけ使う。代表的な場面は次のとおりである。

- 新しい操作を静的ルールへ昇格させたい。
- `harm_detected`が起き、変更によって本当に改善したか確かめたい。
- 予想外に良い結果が続き、どの条件で再現するか見たい。
- release candidateで、重要な方法変更の回帰を確認したい。
- 「CSWが効いた」のか、単にモデルが良い回答を出しただけなのかを、ある程度分けて見たい。

比較はWebチャットだけでも実行できる。

1. 同じ依頼文と同じ資料を用意する。
2. 新しいチャットAでは、領域固有の手法だけで作業する。これをbaselineとする。
3. 新しいチャットBでは、同じ材料にCSWを加える。
4. 可能な範囲で、モデル表示、製品モード、利用可能なツール、実行時期をそろえる。
5. 複数ケースを行う場合は、順序効果を避けるため、baseline先行とCSW先行を交互にする。
6. 必要であれば第三の新しいチャットへ、A/Bのラベルを外した結果だけを渡して比較させる。

Webチャットを完全に再現することはできない。そのため、paired checkも厳密な因果実験とはみなさず、比較可能性を少し高めた観測として扱う。

## 比較するときに見るもの

差を一つの総合点へ潰さず、文章として残す。必要に応じて次の観点を使う。

- **target fidelity**: 対象固有の事実、例外、不可逆性を壊していないか。
- **question gain**: baselineにはなかった、具体的で調べられる問いが生じたか。
- **provenance cleanliness**: 文化体系から生じたものを、対象事実と取り違えていないか。
- **non-forcing**: 空いている位置を埋めるために、対象を読み替えていないか。
- **artifact usefulness**: 実際の文章、設計、調査計画、判断へ使える差が残ったか。
- **residual quality**: 分からないものを無理に閉じず、後から受け取れる形で残せたか。

必要なら尺度を使ってもよいが、平均点や勝敗を方法の価値そのものとはみなさない。文化体系を多く使った出力ほど高得点になるような採点軸も置かない。

## ラウンド記録

ラウンド記録の機械可読形式は`evals/living-lab-round.schema.json`にある。通常ラウンドの例は`evals/living-lab-round.example.json`、paired checkの正常系は`evals/living-lab-paired.example.json`を参照する。

最低限、次を後から追えることを重視する。

- `round_id` / `case_id`
- `mode`: `natural_work`または`paired_check`
- 実行時点と、必要に応じたWebチャット環境
- 課題の短い説明と元資料への参照
- `activation_scope`
- 実際に接触した文化体系と`probe / preview / full / enacted`
- KJの時点記録への参照
- 実作業へ残った成果物
- 残差
- 再開条件

文化体系を開かなかったラウンドも正規の記録である。`non_activation`や`not_loaded`に相当する判断を、失敗として補正しない。

## eventの記録

ラウンドごとにeventを作る必要はない。後の判断を変える可能性がある出来事だけを、`evals/living-lab-event.schema.json`の形式で残す。

- `question_shift`
- `search_shift`
- `kj_reconfiguration`
- `artifact_adoption`
- `decision_change`
- `delayed_reactivation`
- `repeated_transfer`
- `useful_nonuse`
- `harm_detected`

eventは、方法の因果効果を証明するものではない。「何が起き、何を根拠にそう見たのか」を後から追えるようにするための記録である。

過去事例を後から読み直して付けたものは`retrospective`、この観測系をあらかじめ置いた状態で記録したものは`prospective`とする。両者を混同しない。

## 私的記録と公開観測を分ける

実案件のround / eventは、そのまま公開リポジトリへ置くことを前提にしない。私的なチャット、未公開原稿、社内資料、顧客情報などに触れる記録は、原則として`.living-lab/`またはリポジトリ外へ置く。`.living-lab/`はREADMEを除いてGit管理外である。

公開して差し支えない観測だけを`research/living-lab/observations/`へ置く。公開記録は、公開情報だけで構成するか、私的原本とは別に匿名化・抽象化した記録を作る。元資料の本文を複製するより、必要に応じて`chat:case-a-round-3`や`artifact:draft-7`のような不透明な参照を使う。

この区別は、研究上の格付けではない。私的記録と公開記録のどちらも、同じround / event形式を使える。公開できるかどうかと、観測として有用かどうかは別の判断である。

公開観測の集合は、CIでもclosed record setとして検証する。これにより、公開したeventが存在しないroundを参照していないか、IDが重複していないかを継続的に確認できる。

## 記録しないもの

観測のための作業が本体より重くなったなら、この仕組みの設計目的から外れている。原則として次は記録しない。

- すべての発言。
- すべての文化体系候補。
- 使わなかった体系の網羅一覧。
- 単なる言い換えや説明量の増加。
- 同じ資料から派生したカードを、独立した効果として数えたもの。
- 同じ所見が複数体系から出たことを、複数の対象証拠として扱う記録。

「保存は厚く、現在の注意は選択的にする」という原則と、観測記録を増やすことは別である。正本や元材料を保持していても、event記録へすべて転記する必要はない。

## 方法変更へ反映する条件

一つの良い事例だけを見て、すぐに静的ルールを増やさない。方法本文へ昇格させる候補については、少なくとも次を確認する。

1. 異なる複数の実課題で、同じ機能が繰り返し現れたか。
2. 何が良かったのかを、文化体系名ではなく、対象や認知過程に起きた効果として説明できるか。
3. 使わない条件、弱める条件、害が出る条件もある程度分かったか。
4. 既存ルールとの重複ではないか。
5. ルールを追加するより、補助資料、運用上のコツ、dynamicな記録として残す方が適切ではないか。

特に、`repeated_transfer`だけで恒久化を決めない。`useful_nonuse`や`harm_detected`が示す境界も、同じ重さで見る。

## Webチャット固有の注意

- モデルや製品モードは更新される。画面上で分かる範囲だけ環境情報を残し、分からないものは推測しない。
- 別のチャットを使っても、完全に独立した試行にはならない。サービス側の更新や検索結果の変化が混ざる可能性がある。
- 同じチャットでbaselineの後にCSW版を作ると、前の出力が次の作業へ影響する。比較するときは新規チャットを分ける。
- Web検索や接続ツールを使う場合は、可能な範囲で両側の条件をそろえる。ただし、実作業を不自然に縛ってまで統制しない。
- 長期案件では、途中でモデルが変わること自体が普通に起こる。Living Labでは完全な再現性よりも、実作業に何が残ったかを追う。

## 検証

同梱例と手元の記録は、外部依存なしで検査できる。

```bash
# 同梱の natural / paired / event を一つのrecord setとして検査
python scripts/validate_living_lab.py

# 個別ファイルだけを形式検査
python scripts/validate_living_lab.py path/to/round.json path/to/event.json

# 一群の記録としてID重複とevent→round参照まで検査
python scripts/validate_living_lab.py --record-set path/to/round.json path/to/event.json

# 公開観測集合をclosed record setとして検査
python scripts/validate_living_lab.py --record-set research/living-lab/observations/*.json
```

個別検査では、eventに対応するroundが別の保管場所にあってもよい。`--record-set`を付けた場合は、与えたファイル群を一つの閉じた記録集合として扱い、`round_id` / `event_id`の重複と、eventが参照するroundの存在も確認する。

validatorは、研究の質を採点するものではない。必須欄、識別子、enum、paired checkの比較参照、eventの根拠参照など、記録形式上の矛盾を検出するためのものである。

## この仕組みを前景から下げる条件

Living Lab自体を常に前景化する必要はない。方法が安定し、観測を続けても新しい境界や再発パターンがほとんど見つからなくなったら、記録頻度を下げる。

一方、新しい文化体系、新しいモデル世代、新しい用途を導入するときや、過去に問題のあった操作を再導入するときは、必要な部分だけ観測を再び前景化する。
