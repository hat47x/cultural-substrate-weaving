# Web Chat Living Lab

## 位置づけ

Web Chat Living Labは、APIで大量の固定ケースを処理するベンチマークではない。ChatGPTなどのWebチャット上で実際の執筆、調査、設計、分析を進めながら、その途中で何が変わったのかを後からたどれる形で残すための運用観測系である。

目的は、cultural-substrate-weaving（CSW）を高く評価することではない。元資料や成果物へ戻りながら、たとえば次のような変化を確認できる状態を作る。

- 問いが変わった。
- 新しい調査先や観察対象が生じた。
- KJのまとまり、関係、空白が組み替わった。
- 成果物に何かが採用され、後から撤回または変形された。
- 以前の残差が、新しい材料によって再び前景化した。
- 文化体系との接触範囲が変わった。

これらは、まず**出来事**として記録する。その出来事が有用だった、害があった、CSWの効果だったといった評価は、出来事そのものとは分けて扱う。

文化体系を使った数、全文を読んだ回数、体系固有の操作を行った回数、event件数はKPIにしない。

## 観測と評価を分ける

Living Labの記録では、少なくとも次の五つを同じものとして扱わない。

1. **直接観測**：成果物、問い、検索先、KJ配置、発動状態など、後から参照して確かめられる変化。
2. **利用者の判断**：利用者自身が述べた採用、訂正、撤回、違和感など。
3. **生成AIの解釈**：生成AIが出来事に与えた意味、原因説明、有用性や害についての評価。
4. **測定値**：比較や計測によって実際に記録された値。
5. **測定への評価**：その値をどう解釈するかという、別の判断。

生成AIの判断も記録してよい。ただし、利用者の判断や測定値と同じ来歴へ混ぜない。生成AIが評価軸を作り、自分の出力を採点し、その結果を説明した場合も、採点された値と、その値への解釈を分けて残す。

## 二つの運用モード

### `natural_work`

通常はこちらを使う。現実の作業を止めず、自然な流れの中で観測する。

一つのラウンドでは、おおむね次のように進める。

1. 新しい資料、観察、反証、実行結果など、今回増えた材料を見る。
2. 新材料が古い残差や孤立カードに触れた場合は、必要な部分だけを前景へ戻す。
3. KJと文化体系を、その時点の作業に必要な形で使う。
4. 成果物、判断、調査方針など、実作業の側で実際に何が変わったのかを見る。
5. 残差と再開条件を、誰の判断なのか後からたどれる形で残す。
6. 後から経過をたどる意味がある変化が起きた場合だけ、eventを記録する。

毎回、過去の履歴をすべて読み直したり、記録欄をすべて埋めたりする必要はない。

### `paired_check`

方法変更の判断材料として、同じ課題に対する差を、もう少し比較しやすい形で見たい場合に使う。

1. 同じ依頼文と同じ資料を用意する。
2. 新しいチャットAでは領域固有の手法だけで作業し、baselineとする。
3. 新しいチャットBでは、同じ材料にCSWを加える。
4. 可能な範囲で、モデル表示、製品モード、利用できるツール、実行時期をそろえる。
5. 複数ケースを扱う場合は、順序効果を後から確認できるよう、実行順を記録する。
6. 必要であれば、第三のチャットで結果を比較する。

Webチャットを完全に再現することはできない。そのため、paired checkも厳密な因果実験とはみなさず、比較しやすさを少し高めた観測として扱う。

第三のAIチャットによる比較も、客観的な測定結果そのものではない。そこで述べられた評価は、`interpretations`にAI由来の判断として記録する。

## paired checkの記録を分ける

schema 0.2では、比較結果を次の三つに分ける。

- `observed_differences`：出力同士を参照すれば確認できる差。
- `measurements`：数値、真偽値、文字列などとして実際に記録した測定値と、その出所。
- `interpretations`：その差や値に対する判断。`source_type`と出所を付ける。

たとえば、「treatmentにはbaselineにない質問が1件ある」という記録と、「その質問はCSWによって生まれたのでtreatmentの方が優れている」という評価は同じではない。

## ラウンド記録

機械可読形式は`evals/living-lab-round.schema.json`にある。通常の例は`evals/living-lab-round.example.json`、paired checkの例は`evals/living-lab-paired.example.json`を参照する。

最低限、次のことを後からたどれるようにする。

- `round_id` / `case_id`
- `mode`
- 実行時点と、必要に応じたWebチャット環境
- 課題の短い説明と元資料への参照
- `activation_scope`
- 実際に接触した文化体系と`probe / preview / full / enacted`
- KJ時点記録への参照
- 実作業に残った成果物
- 出所付きの制約、残差、再開条件
- 必要に応じた、出所付きの解釈

`activation_scope: non_activation`は、そのラウンドで文化体系を開かなかったという状態を表す。それだけを根拠に、「使わない方がよかった」「有用だった」「害を避けた」とは判断しない。

## eventの記録

ラウンドごとにeventを作る必要はない。後から経過をたどる意味がある出来事だけを、`evals/living-lab-event.schema.json`の形式で残す。

- `question_shift`
- `search_shift`
- `kj_reconfiguration`
- `artifact_adoption`
- `artifact_withdrawal`
- `decision_change`
- `delayed_reactivation`
- `repeated_transfer`
- `framework_contact_change`

schema 0.2では、`useful_nonuse`と`harm_detected`をevent種別として用いない。前者は非発動という状態と有用性の評価を、後者は出来事と害の評価を、一つの名称にまとめていたためである。

eventの`observation`には、できるだけ後から参照して確かめられる変化を書く。評価や原因説明も残す必要がある場合は`interpretations`へ分け、`source_type`を付ける。

過去の事例を後から読み直して付けたeventは`retrospective`、あらかじめ観測系を置いた状態で記録したeventは`prospective`とする。この区別も品質の順位ではない。

## `source_type`

出所付きの判断には、次の値を使う。

- `user`：利用者自身が述べた判断。
- `ai`：生成AIが加えた判断や解釈。
- `external`：外部資料や外部評価者に由来する判断。
- `mixed`：複数の起源を分離できない、または共同して成立した判断。
- `unknown`：現在の記録だけでは起源を特定できない判断。

これは信頼度を順位付けするための値ではない。`user`だから事実、`ai`だから無価値という意味でもない。**後から、誰の判断だったのかを取り違えないための来歴**である。

## 私的記録と公開観測を分ける

実案件のround／eventは、そのまま公開リポジトリへ置くことを前提にしない。私的なチャット、未公開原稿、社内資料、顧客情報などに触れる記録は、原則として`.living-lab/`またはリポジトリ外に置く。

公開して差し支えない観測だけを`research/living-lab/observations/`に置く。公開記録は公開情報だけで構成するか、私的な原本とは別に、匿名化・抽象化した記録を作る。

公開できるかどうかと、その観測が後の検討にどの程度役立つかは、別の判断である。

## 記録しないもの

観測のための作業が本体より重くなったなら、この仕組みの目的から外れている。原則として、次のものは記録しない。

- すべての発言。
- すべての文化体系候補。
- 使わなかった体系の網羅一覧。
- 単なる言い換えや説明量の増加。
- 同じ資料から派生したカードを、独立した効果として数えたもの。
- 同じ所見が複数の体系から出たことを、複数の対象証拠として扱う記録。

正本や元材料を厚く保存することと、event記録へすべて転記することは別である。

## 方法変更へ反映する前に

一つの事例や、一つのAI評価だけを見て、静的ルールを増やさない。

方法変更を検討するときは、少なくとも次の点へ戻る。

1. 利用者がどのような採用、訂正、撤回を行ったか。
2. 成果物やKJ配置に、後から確認できる差が実際にあるか。
3. 同じ働きが、別の実課題でも現れたか。
4. AIによる評価ではなく、元資料へ戻ってその差を説明できるか。
5. 既存ルールとの重複ではないか。
6. 静的ルールを増やすより、事例、補助資料、動的記録として残す方が適切ではないか。

測定値がある場合も、その値とAIによる意味づけを分ける。測定という形式を取っているだけで、方法の有効性や因果が確定したとはみなさない。

## Webチャット固有の注意

- モデルや製品モードは更新される。画面上で分かる範囲だけ環境情報を残し、分からないことは推測しない。
- 別のチャットを使っても、完全に独立した試行にはならない。
- 同じチャットでbaselineの後にCSW版を作ると、前の出力が次の作業へ影響する。比較が必要な場合は、新しいチャットを分けて使う。
- Web検索や接続ツールを使う場合は、可能な範囲で条件をそろえる。ただし、実作業を不自然に縛ってまで統制しない。
- 長期案件では、途中でモデルが変わることもある。完全な再現性を前提にしない。

## 検証

同梱例と手元の記録は、外部依存なしで検査できる。

```bash
python scripts/validate_living_lab.py
python scripts/validate_living_lab.py path/to/round.json path/to/event.json
python scripts/validate_living_lab.py --record-set path/to/round.json path/to/event.json
python scripts/validate_living_lab.py --record-set research/living-lab/observations/*.json
```

validatorが確認するのは、schema、必須項目、enum、参照関係などの形式上の契約である。**validatorを通ったことは、観測内容や生成AIの評価が正しいことを意味しない。**
