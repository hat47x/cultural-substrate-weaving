# Web Chat Living Lab

## 位置づけ

この仕組みは、APIを使って大量の固定ケースを回すベンチマークではない。ChatGPTなどのWebチャット上で実際の執筆・調査・設計・分析を進めながら、cultural-substrate-weaving（CSW）が仕事の流れへどのような差を生むかを、必要な粒度だけ残していくための運用観測系である。

主目的は、方法を高得点に見せることではない。次を後から確かめられる状態を作ることにある。

- どの問いが変わったか。
- 何を新しく探すようになったか。
- KJのまとまりや空白が後から組み替わったか。
- 実際の成果物や判断へ何が残ったか。
- どの操作は使わない方がよかったか。
- その場では意味が分からなかった残差が、後から効いたか。

したがって、文化体系の利用数、全文を読んだ回数、体系固有操作を実行した回数、event件数はKPIにしない。

## 二つの運用モード

### `natural_work`

通常はこちらを使う。現実の仕事を止めず、自然な流れでCSWを使う。

一つのラウンドで必要なのは、おおむね次だけである。

1. 新しい資料・観察・反証・実行結果など、今回増えた材料を見る。
2. その材料が以前の残差や孤立カードへ触れた場合だけ、必要な部分を前景へ戻す。
3. KJと文化体系を、現在の問いに必要な範囲だけ使う。
4. 成果物、判断、調査方針など、実作業側へ何が残ったかを見る。
5. 未解決事項と、再び開く条件を残して区切る。
6. 後から意味を持ちそうな変化が実際に起きた場合だけeventを記録する。

毎回、過去履歴を全文読解したり、全欄を埋めたりする必要はない。

### `paired_check`

方法変更の判断にもう少し強い比較が必要なときだけ使う。代表例は次である。

- 新しい操作を静的ルールへ昇格させたい。
- `harm_detected`が起き、変更が本当に改善か確かめたい。
- 予想外に良い結果が続き、再現条件を見たい。
- release candidateで、重要な方法変更の回帰を確認したい。
- 「CSWが効いた」のか、単にモデルが良い回答を出しただけなのかを少し分けたい。

比較はWebチャットだけで実行できる。

1. 同じ依頼文、同じ資料を用意する。
2. 新しいチャットAでは、領域固有手法だけで作業する。これをbaselineとする。
3. 新しいチャットBでは、同じ材料にCSWを加える。
4. 可能な範囲で、モデル表示、製品モード、利用可能なツール、実行時期を揃える。
5. 順序効果を避けるため、複数ケースを行う場合はbaseline先行とCSW先行を交互にする。
6. 必要なら第三の新しいチャットへ、A/Bのラベルを外した結果だけを渡して比較させる。

Webチャットは完全には再現できない。そのため、paired checkも厳密な因果実験とはみなさない。比較可能性を少し高めた観測として扱う。

## 比較時に見るもの

単一の総合点へ潰さず、差分を文章で残す。必要なら次の観点を使える。

- **target fidelity**：対象固有の事実・例外・不可逆性を壊していないか。
- **question gain**：baselineには無かった、具体的で調べられる問いが生じたか。
- **provenance cleanliness**：文化体系から生じたものを対象事実へ取り違えていないか。
- **non-forcing**：空位置を埋めるために対象を読み替えていないか。
- **artifact usefulness**：実際の文章、設計、調査計画、判断へ使える差が残ったか。
- **residual quality**：分からないものを無理に閉じず、後から受け取れる形で残せたか。

必要なら尺度を使ってもよいが、平均点や勝敗を方法の価値そのものとみなさない。特に、文化体系を多く使った出力が高得点になるような採点軸を置かない。

## ラウンド記録

ラウンド記録の機械可読形式は `evals/living-lab-round.schema.json` にある。通常ラウンドの例は `evals/living-lab-round.example.json`、paired checkの正常系は `evals/living-lab-paired.example.json` を参照する。

最低限、次を追えることを重視する。

- `round_id` / `case_id`
- `mode`: `natural_work` または `paired_check`
- 実行時点と、必要ならWebチャット環境
- 課題の短い説明と元資料参照
- `activation_scope`
- 実際に接触した文化体系と `probe / preview / full / enacted`
- KJ時点記録への参照
- 実作業へ残った成果物
- 残差
- 再開条件

文化体系を開かなかったラウンドも正規の記録である。`non_activation`や`not_loaded`相当の判断を、失敗として補正しない。

## event ledger

ラウンドごとにeventを作る必要はない。後の判断を変えうる出来事だけを `evals/living-lab-event.schema.json` の形式で残す。

- `question_shift`
- `search_shift`
- `kj_reconfiguration`
- `artifact_adoption`
- `decision_change`
- `delayed_reactivation`
- `repeated_transfer`
- `useful_nonuse`
- `harm_detected`

eventは、方法の因果効果を証明するものではない。「何が起き、何を根拠にそう見たか」を後から追えるようにする記録である。

過去事例を後から読み直して付けたものは `retrospective`、事前にこの観測系を置いた状態で記録したものは `prospective` とする。両者を混同しない。

## 記録しないもの

観測のための作業が本体より重くなったら、この仕組みの設計目的から外れている。原則として次は記録しない。

- すべての発言。
- すべての文化体系候補。
- 使わなかった体系の網羅一覧。
- 単なる言い換えや説明量の増加。
- 同じ資料から派生したカードを独立した効果として数えたもの。
- 同じ所見が複数体系から出たことを、複数の対象証拠として扱う記録。

「保存は厚く、現在の注意は選択的にする」という原則と、観測記録を増やすことは別である。正本や元材料を保持していても、ledgerへ全件転記する必要はない。

## 方法変更へ反映する条件

一つの良い事例から、すぐに静的ルールを増やさない。方法本文への昇格候補は、少なくとも次を検討する。

1. 異なる複数の実課題で同じ機能が繰り返し現れたか。
2. 何が良かったのかを、文化体系名ではなく対象・認知過程上の効果として説明できるか。
3. 使わない条件、弱める条件、害が出る条件もある程度分かったか。
4. 既存ルールとの重複ではないか。
5. ルール追加より、補助資料・運用上のコツ・dynamicな記録として残す方が適切ではないか。

とくに、`repeated_transfer`だけで恒久化を決めない。`useful_nonuse`や`harm_detected`が示す境界も同じ重さで見る。

## Webチャット固有の注意

- モデルや製品モードは更新される。画面上で分かる範囲だけ環境情報を残し、分からないものを推測しない。
- 別チャットでも完全な独立試行にはならない。サービス側の更新や検索結果の変化が混ざりうる。
- 同じチャットでbaselineの後にCSW版を作ると、前の出力が次へ影響する。比較時は新規チャットを分ける。
- Web検索や接続ツールを使う場合は、可能な範囲で両側の条件を揃える。ただし、現実の作業を不自然に縛ってまで統制しない。
- 長期案件では、モデル変更をまたぐこと自体が普通である。Living Labは完全な再現性より、実作業で何が残ったかを追う。

## 検証

同梱例と手元の記録は、外部依存なしで検査できる。

```bash
# 同梱の natural / paired / event を一つのrecord setとして検査
python scripts/validate_living_lab.py

# 個別ファイルだけを形式検査
python scripts/validate_living_lab.py path/to/round.json path/to/event.json

# 一群の記録としてID重複とevent→round参照まで検査
python scripts/validate_living_lab.py --record-set path/to/round.json path/to/event.json
```

個別検査では、eventの対応roundが別の保管場所にあってもよい。`--record-set`を付けた場合は、与えたファイル群を一つの閉じた記録集合として扱い、`round_id` / `event_id` の重複と、eventが参照するroundの存在も確認する。

validatorは、研究の質を採点するものではない。必須欄、識別子、enum、paired checkの比較参照、eventの根拠参照など、記録形式上の矛盾を検出するためのものである。

## この仕組みの終了条件

Living Lab自体を常時前景化する必要はない。方法が安定し、観測を続けても新しい境界や再発パターンがほとんど出なくなったら、記録頻度を下げる。

一方、新しい文化体系、新しいモデル世代、新しい用途、過去に問題のあった操作を再導入するときは、必要な部分だけ観測を再び前景化する。
