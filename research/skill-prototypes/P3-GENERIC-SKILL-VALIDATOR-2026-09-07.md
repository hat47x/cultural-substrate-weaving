# P3 Generic Skill validator — 2026-09-07

## 目的

production builderをmulti-Skill対応可能な内部構造へ進めても、validatorが単一CSWのpathを直接組み立て続けると、companion Skill追加時に「生成はされたが検査されない」領域が生まれる。

現行`validate.py`では特に次が単一Skill前提になっている。

- OpenAI reference projectionを`config["name"]`のSkillだけについて検査する。
- OpenAI `SKILL.md` byte budgetを`config["name"]`だけへ適用する。
- Claude byte budgetをlocale catalogの`skill_name = weave`一つへ適用する。

一方、この段階でresearch companionをproduction検査対象へ追加すると、production昇格判断とvalidator mechanicsの変更が混ざる。

そこで、**現在の検査対象をCSW一つのまま維持し、Skill artifactに対する検査操作だけを解決済みpathへ適用できるhelperへ切り出す。**

## 変更

### `check_projected_reference(...)`

解決済みの

- source file
- generated reference file
- source表示ラベル

を受け取り、現行と同じ二つを検査する。

1. generated referenceが存在する。
2. generated byte列がsourceと一致する。

このhelperはSkill名、profile、locale、manifest moduleを知らない。

現在の`check_modules()`は従来どおりcanonical manifestを読み、CSW OpenAI interactive / meteredのpathを組み立ててhelperへ渡す。

つまりsource discoveryの意味は変えない。

### `check_skill_entry_budget(...)`

解決済みの

- `SKILL.md` path
- max bytes
- error表示ラベル

を受け取り、byte sizeを返しつつ上限超過を検査する。

現在は従来どおり、

- CSW OpenAI interactive
- CSW OpenAI metered
- CSW Claude `weave`

だけへ適用する。

Claude sizeは従来のvalidation report metric `claude_skill_bytes`へ同じ値を返す。

## 検査範囲を変えない

このPRでは次を増やさない。

- 検査対象Skill数
- OpenAI profile数
- Claude plugin内Skill数
- token budget項目
- validation report schema / metric名
- marketplace検査
- link検査
- canonical source検査
- translation検査

`tests/test_build.py`の

```text
plugin内Skill数 = 1
generated Skill path数 = 6
```

というproduction contractも維持する。

この単一Skill assertionをgeneric validator化と同時に外すと、未昇格のcompanionがproduction artifactへ混入しても見逃せるため、まだ変更しない。

## Error semantics

既存のproduction validation error wordingを維持する。

OpenAI generated referenceでは、

```text
Missing generated reference: ...
Generated reference differs from <locale>/<source>
```

を保つ。

byte budgetも、呼び出し側が従来と同じlabelを渡すことで、

```text
<locale>: OpenAI <profile> SKILL.md exceeds budget: ...
<locale>: Claude SKILL.md exceeds budget: ...
```

を保つ。

mechanical refactorを理由にvalidation reportの差分を発生させない。

## Tests

`tests/test_skill_validation_helpers.py`でhelper単体について次を確認する。

- byte一致したreferenceは通る。
- missing targetを検出する。
- byte mismatchを検出する。
- budget内ではerrorを出さずsizeを返す。
- budget超過ではcaller supplied labelとsizeを返す。

これらはproduction対象Skillを増やすテストではない。

## Builder refactorとの関係

P3のmechanical boundaryは対になる。

```text
writer
  解決済みSkill inputs → runtime Skill tree

validator
  解決済みruntime paths → reference / budget checks
```

どちらもこの段階では、

> どのSkillをproduction対象とするか

を所有しない。

現在は既存CSWのmanifest / locale adapterがその対象を決める。

将来、production suite descriptorを導入する場合には、同じdescriptorから

- writerへ生成対象を渡す。
- validatorへ検査対象を渡す。

という対称性を作れる。

## Research suiteをまだproduction dependencyにしない

`research/skill-prototypes/suite-manifest.json`にはすでに三Skillのpackage source / target contractがある。

しかし本PRでは`validate.py`からresearch manifestを読まない。

理由は、

- research candidateの存在
- production publication boundary

をまだ同一視しないためである。

research evidenceとpackage probeが十分になった後、production用descriptorを独立して設計する。

## 次の段階

writerとvalidatorのmechanicsが複数Skillを扱える形へ分かれた後、次に検討するのは**production candidate descriptor**である。

そのdescriptorでは、少なくとも次を混同しない必要がある。

1. Skill identity
2. source realization
3. locale availability
4. host target name
5. host metadata maturity
6. production inclusion state

特に`prototype realization exists`を`production inclusion = true`へ自動変換しない。

最初のdescriptorはcurrent CSWだけをproduction-enabledとして表し、Affinity / Iterativeをcandidateとして参照するだけでもよい。

その段階でbuilder / validator双方が同じproduction-enabled集合を読むようになれば、単一Skill pathの暗黙前提を外しながら公開物はなお一つに保てる。

## canonical migrationとの順序

```text
P2 research suite / package probes
        ↓
P3 generic Skill writer
        ↓
P3 generic Skill validator   ← 本変更
        ↓
production candidate descriptor
        ↓
companion promotion gate
        ↓
canonical CSW責務分離
```

KJ法由来のone-round synthesisやmulti-round inquiryをcanonical CSWから削るのは、build/validation mechanicsとpromotion boundaryが揃った後に行う。

## 結論

**validatorのmulti-Skill化は、Skill数を増やすことから始めず、現在と同じCSW一つの検査を解決済みartifactへ適用するgeneric operationへ切り分ける。**

これにより、将来のproduction descriptorが複数Skillを列挙したときに、生成だけ増えて検査が追随しない状態を避ける準備を、公開artifactを変えずに進める。
