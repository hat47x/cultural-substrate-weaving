# Aristotle's four causes runtime requalification profile

Status: profile-ready / research-only / no-runtime

## Identity

- names: アリストテレス四原因 / Aristotle's four causes
- current scope: Aristotle's material, formal, efficient, and final aitiai as distinct explanatory answers to a why-question
- current runtime use: split an overloaded explanation into material/resource, structure/form, change-producing mechanism, and purpose/end questions
- not intended use: treating all four as modern scientific causes, inferring purpose where the target has none, or requiring every target to instantiate four independent boxes

## Source basis

### Stanford Encyclopedia of Philosophy — Aristotle on Causality

https://plato.stanford.edu/entries/aristotle-causality/

The entry distinguishes material, formal, efficient, and final causes as different kinds of answers to explanatory why-questions. It also emphasizes that more than one kind can enter an adequate explanation and that some causes can coincide.

### Stanford Encyclopedia of Philosophy — Aristotle's Metaphysics

https://plato.stanford.edu/entries/aristotle-metaphysics/

This provides broader context for form, matter, actuality, potentiality, and explanatory structure. CSW does not transfer Aristotelian metaphysics into target domains.

## Structural core under requalification

The current CSW use can be de-bound as five operations:

1. split one vague "why" into different explanatory jobs;
2. ask whether resource/material constraints have been named;
3. ask whether organization/structure/algorithm has been named;
4. ask what process, event, or mechanism produces the change;
5. ask what explicit stakeholder or design purpose the artifact is meant to satisfy.

The runtime question is whether this remains distinct from strong ordinary systems/design review.

## Native operation candidates

### why-splitting

Separate several explanation types instead of accepting one overloaded cause statement.

### explanation-gap

Look for an explanatory dimension that the current analysis omitted.

### causal-category-audit

Detect when purpose, mechanism, structure, and material/resource constraints are being mixed.

### multi-cause-composition

Allow several complementary explanations to coexist without forcing one winner.

### artifact-design-probe

For an engineered artifact, inspect resources/materials, architecture/form, producing/operating mechanism, and purpose.

## Target-return questions

- Which target-side purpose is documented, and by whom?
- Which physical, computational, budgetary, or environmental constraints matter?
- Which architecture, algorithm, or organization defines what the artifact is?
- Which event, process, actor, or mechanism produces the relevant change?
- Are two different explanation jobs being collapsed into the word "cause"?
- Would ordinary stakeholder/requirements/architecture/behavior review expose the same gaps?
- If all Aristotelian labels are removed, what target-side question remains that the ordinary baseline did not already ask?

## Historical / interpretive boundary

- Aristotle's aitia is broader than the narrow modern sense of efficient causation.
- Formal and final causes can interact or coincide; CSW must not force four independent boxes.
- Final cause is historically stronger than ordinary modern "documented stakeholder purpose"; the latter is a deliberate de-binding, not a claim of conceptual identity.
- Later Aristotelian, scholastic, scientific, and design-theory uses should not be collapsed into Aristotle's own account.
- The framework does not license teleology in natural or social targets without evidence.

## What not to import by default

- a four-slot checklist as a universal ontology;
- purpose where no agent, requirement, or target-side end is documented;
- structure as if it were a causal mechanism;
- material/resource constraints as if they alone explained behavior;
- an assumption that explanatory completeness means all four categories are filled;
- Aristotelian metaphysical claims as engineering facts.

## De-binding

1. remove material/formal/efficient/final labels unless provenance matters;
2. restate them as target-side resource/constraint, structure/architecture, mechanism/process, and documented purpose questions;
3. do not invent a purpose to fill a slot;
4. mark which explanatory claims are evidence-backed;
5. preserve multiple explanations when the target supports them;
6. compare the resulting questions with ordinary systems/design review;
7. keep only distinctions that survive that baseline.

## Runtime requalification result

For the tested SIer artifact-design target, the strong ordinary baseline reproduces the current target-relevant operations.

NASA systems engineering already separates stakeholder expectations and objectives, technical requirements and constraints, logical decomposition, and design solution. Ordinary behavior/mechanism review supplies the change-producing question. Together these reproduce the de-bound material/resource, structural, mechanism, and purpose distinctions.

No additional target-side question remains that requires the Aristotelian substrate for this use.

The strongest residue is historical explanatory vocabulary and a compact philosophical reminder that "why" is not one question. That remains useful for explicit Aristotle, history-of-philosophy, comparative explanation, or educational work, but it does not currently justify general default runtime selection complexity for SIer design analysis.

The former runtime dossier has now been removed from the default corpus. The comparison above establishes capability overlap with ordinary systems/design review after the relevant explanatory jobs are named.
