# Paṭṭhāna conditional relations vs dependent origination vs four causes vs ordinary dependency analysis

Status: research differentiation / no runtime promotion

## Purpose

These approaches can all be described loosely as "causal analysis." That label is too broad for CSW.

The comparison asks what each contact preserves and what kind of target-return question it is designed to create.

## Core distinction

| Framework / baseline | Primary object | Characteristic operation | Typical target-return |
|---|---|---|---|
| Dependent origination | condition chain / upstream establishment and cessation | move upstream and test what ceases when a condition ceases | "which upstream condition must be removed or changed?" |
| Theravāda Paṭṭhāna candidate | network of conditioning/conditioned states with differentiated relation modes | preserve convergence, fan-out, simultaneity/sequencing, mutuality, and relation-mode uncertainty | "these four dependencies all matter, but do they operate in the same way?" |
| Aristotle four causes | plural explanatory answers to one why-question | separate material / formal / efficient / final explanatory jobs | "which kind of explanation is missing?" |
| ordinary typed dependency graph / fault tree | target-authored nodes and relation types | model dependencies or failure combinations directly | "which edge or cut set is supported by evidence?" |

## Same target, different operations

Target:

> A distributed scheduler sometimes dispatches work to a worker that cannot complete it after a rolling deployment.

### Dependent-origination pass

Move upstream from failed execution:

- failed execution;
- worker not usable;
- credential state invalid;
- refresh did not propagate.

The useful question is whether removing or repairing an upstream condition stops the failure.

### Four-causes pass

Split the explanation:

- what material/runtime substrate was present?
- what configuration or structure defined the behaviour?
- what process/event triggered it?
- what intended operational purpose shaped the design?

This is explanation pluralism, not a dependency-network analysis.

### Paṭṭhāna-inspired pass

Keep several distinct conditioning relations visible:

- credential validity supports request acceptance;
- cached capability persists from an earlier observation;
- heartbeat freshness co-determines eligibility;
- store revision constrains transition authority;
- queue redelivery creates a later opportunity but does not own task truth.

The primary gain is not "more causes." It is keeping the **mode of conditioning** inspectable.

### Ordinary typed dependency graph

Represent the same nodes and relation types in target language.

If this baseline produces the same distinctions, tests, and residual questions with less overhead, Paṭṭhāna contact has not earned runtime inclusion.

## Non-substitutability

### Paṭṭhāna cannot replace dependent origination

A dense relation map may make it harder to see the simplest upstream intervention or cessation counterfactual.

### Dependent origination cannot always replace Paṭṭhāna

A linear or mostly linear chain can collapse several co-present, reciprocal, or differently typed conditions into one arrow.

### Four causes cannot replace either

Explanatory categories answer a different question from relation topology and condition mode.

### Cultural contact cannot replace ordinary engineering analysis

CSW must still use logs, tests, traces, architecture contracts, FTA, dependency graphs, or domain-specific evidence where those are the appropriate tools.

## Strong counter-hypothesis

The candidate may fail to remain distinct after de-binding.

If "Paṭṭhāna contact" repeatedly reduces to:

- create nodes;
- type edges;
- show multiple incoming edges;
- ask for evidence;

then an ordinary typed dependency graph is probably the better runtime instrument.

The cultural candidate should remain useful only if its contact reliably prompts analysts to inspect relation-mode differences they would otherwise collapse, without forcing the twenty-four-condition taxonomy.

## Runtime decision

No runtime promotion.

First compare against:

- current dependent-origination pass;
- ordinary typed dependency graph / fault-tree review;
- mixed incidents containing sequential, co-present, shared, and reciprocal dependencies;
- simple incidents where non-activation should win.
