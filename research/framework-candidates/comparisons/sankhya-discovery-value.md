# Sāṅkhyaの接触前の方法選択と発見価値

Status: 2026-10-18研究メモ / 仮想対象の机上レビュー。独立実行・効果測定・採用判断なし。

## 同一対象

[固定の仮想注文成功率問題](../worked-examples/sankhya-layer-observer.md)を使う。UI指標の低下、gateway counterとの不一致、event→正規化→分類→集計→viewer filter、10:00の分類設定変更、部署A/Bの表示差が**体系接触前からすべて与えられている**。

これを隠して、通常レビューが表面のUIしか見ないと仮定してはいけない。

## A — 一般の障害調査として開始した場合

体系名や生成層の語彙を与えなくても、「何を成功と数えているか」「業務上の実処理と集計結果は一致するか」「部署間で指標の定義や対象範囲が一致するか」「変更が原因か単に同時刻の事象か」は、普通のmetric reviewとdata pipeline debuggingの初回から挙がり得る。対象の記述自体が観測値の生成過程を明記しているため、data lineageを選ぶことも自然である。

これは独立した担当者の回答記録**ではない**。その手法が自然に選ばれるだろうという、本資料作成者の再現可能な机上の見立てである。

## B — Sāṅkhyaに接触した場合

古典体系のpuruṣa/prakṛtiと生成系列に接触し、CSWが借りる「観測位置と生成過程を切り分ける」「目に見える指標から上流へ遡る」構造を開く。生成された次の問いは、既存の通常手法が既に扱える。

- 「注文の成功」と「表示上の成功」の定義・分母の差。
- 10:00の変更で変わった分類規則と、業務処理自身の状態の差。
- 部署A/Bが見た指標の対象範囲と、見ている人に依存したfilterの差。
- 分類規則が原因なのか、より上流の入力event・欠損に起因するか。

体系に由来する問いが具体的でも、**これらが初めて生成されたことも、実際の障害を見つけたこともまだ観測していない**。

## C — 使わない判断

同一対象について、通常のSRE/data lineageが初回から上記の区別を開いている場合には、Sāṅkhyaを追加しても説明の語彙だけが増える。コスト増や不適切な形而上学の輸入を避け、[非適用例](../worked-examples/sankhya-non-activation.md)に従い非活性化する。

三guṇaを固定的な「静的・動的・調和」といったソフトウェアの三分類へ強制するのは、実対象に三つの独立した意味ある変数が与えられていない限り適用外とする。

## 判断を再開するのに必要な証拠

1. 今回の同じ材料を、文化体系や予想される質問を見ていない独立のレビュー担当へ先に提示し、自然に選んだ方法、初回質問、未確認点を原文で記録する。
2. 別のレビュー条件で体系由来の候補質問を保存し、**同じ問いの言い換え**と実質的に新しい検査可能な問いを分ける。
3. 新しい問いがあれば、元のraw receipts、分類規則、filter、集計SQL等へ戻して、対象側の支持・反証・不明を独立に判断する。
4. 手法の事後再現可能性と事前選択を別欄に残し、レビュー担当や事例を変えたときの再現性を未実施と明記する。

## 現時点の結論

**能力の重複は大きい。** 指標とETLを扱うこの対象では、通常の専門方法が体系への接触前から自然に選ばれると考える理由がある。従って追加の発見価値を肯定する根拠はなく、現行の「表面の症状に留まる普通の分析」という仮説は厳しく再検討を要する。

ただしこれは独立した発見実験ではなく、否定的な机上仮説評価でも正式な降格決定でもない。Registryの `adopted` と `unreviewed_hypothesis` を維持する。
