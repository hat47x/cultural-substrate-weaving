# Pāṇini Aṣṭādhyāyī rule architecture target-return example

Status: hypothetical / profile-readiness support

ある業務システムでは、外部へ出力するレコードに対して複数の規則を適用する。

仕様書には、章の見出しとして「外部出力するすべてのレコード」があり、その下に次の規則が並ぶ。

- `internal_note`を削除する。
- 監査保管用の出力では`internal_note`を保持する。
- 出力内容を確定した後に署名する。

旧実装では、章見出しの条件を共有したまま一つの処理として実装していた。

移行先では規則を個別のYAMLへ分割した。このとき、一つ目の規則だけに「外部出力」の条件が明記され、二つ目と三つ目では章見出しから継承していた条件が失われた。また、署名処理が変換処理より先に実行される構成になった。

Pāṇiniの規則構造から着想したpassでは、Sanskritの用語を対象へ持ち込まず、見出しから継承されていた条件を各規則へ展開する。次に、削除の一般規則と監査保管用の限定規則が同じ対象へ適用される条件を列挙する。どちらを優先するかは推測せず、対象の仕様と既存テストへ戻す。署名の順序条件も、データ変換規則とは別の適用制御として記録する。

このpassが返すのは、「Pāṇiniの体系ではこの実装が誤りである」という判断ではない。

対象側へ返す問いは、次のようになる。

- 監査保管用出力は、削除規則の例外として仕様に明記されているか。
- 分割後の各YAMLに、元の章見出しが担っていたscopeが保存されているか。
- 署名は変換前と変換後のどちらを対象にする、と仕様で定義されているか。
- この優先関係と順序を固定する回帰テストがあるか。

文化固有語を外した後にも、継承scopeと規則相互作用という対象側の確認事項が残るため、この例では候補の探索operationが成立する。
