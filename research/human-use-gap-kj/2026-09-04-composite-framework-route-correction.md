# 複数体系compositionの静的欠落判定を訂正する

- Date: 2026-09-04
- Status: research correction / runtime reachability residual
- Related: Issue #69, Issue #144, PR #145, PR #146, `2026-09-01-r3-capability-preservation-inventory.md`, `2026-09-04-composite-framework-fields.md`, `2026-09-04-composite-framework-layering-rebaseline.md`, `src/ja-JP/ROUTER.md`, `src/ja-JP/methods/transformation.md`

## 訂正すること

PR #145とPR #146では、複数体系compositionを改めて前景化する過程で、`system-selection.md`と`framework-application.md`を中心に読み、複数体系を役割分離して重ねる操作が現行正本では暗黙である、という方向へ問題を置いた。

この読みは強すぎた。

現行 `src/ja-JP/methods/transformation.md` へ戻ると、複数体系についてすでに次の能力が明示されている。

- 深さの異なる層を区別し、**層ごとに別の体系を使い、共通する変化原理で統合する**。
- **直交する体系を重ねることを積極的に試す**。
- 複数体系を組み合わせる場合は、**軸の独立性を確認する**。
- 二つ目以降の体系には、**一つ目では扱えない情報種別を担当させる**。
- 同じ分類原理の体系を重ね、確証だけを増やすことを避ける。
- 連続体系同士を交差させる場合や、空欄の多いマトリクスを保持する場合も扱う。

さらに `2026-09-01-r3-capability-preservation-inventory.md` は、旧 `creative-patterns.md` にあった「層ごとに別体系を使って統合する」能力をすでに棚卸しし、**現コアへ吸収済み**と明記している。

したがって、役割分離型や直交重層を「現行runtimeに足りない静的能力」とみなすことは撤回する。

## なぜ読み違えたか

原因は、今回の探索経路そのものにある。

PR #127後の残差を調べる際、

1. `system-selection.md` のcandidate recall。
2. `framework-application.md` の探索／帰属、状態格子、`cross_field_emergent`。

の間に何がないかを重点的に見た。

そのため、別ファイルである `transformation.md` にすでに置かれていた、

> 候補体系を複数使うとき、それぞれへ異なる情報種別を担当させ、直交する体系を重ねる

という能力へ十分に戻らないまま、「候補想起」と「複数体系の出口」の間にcomposition演算が欠けていると読んだ。

これは、研究方法上の重要な失敗である。

> **隣接する二つのmoduleの間だけを見て空白を立てると、別moduleへ既に外在化された能力を欠落と誤認できる。**

「元材料へ戻る」は、人的成果物だけでなく、**現行正本全体と既存の棚卸し記録へ戻ること**も含まなければならない。

## PR #145の扱い

`2026-09-04-composite-framework-fields.md`で得た次の研究内容は残す。

- 候補を複数想起することと、複数軸を一つの状態空間へ構成することは別の認知操作である。
- Tzolk’in、Calendar Round、十干十二支、『易』から、組合せには全直積、周期結合、制約付き組合せなど異なる型があることを確認した。
- 空セルを読む前に、そのセルがcomposition rule上の有効状態か確認する必要がある。
- CSWが作った体系間交差を、伝統上の既存対応へ逆輸入しない。

これらは、現行 `transformation.md` が持つ複数体系能力を**細かく読み直す研究材料**としては有効である。

ただし、ここから「現行正本にcomposition能力がない」とは導かない。

## PR #146の扱い

`2026-09-04-composite-framework-layering-rebaseline.md`で確認した自然利用も残す。

- 私的な創作成果物に、複数体系へ異なる認知役割を持たせて同じ対象へ重ねる構成があった。
- 別の設計ドメインでも、複数体系が状態変化、生成と制約、経路と中間点など異なる設計問いを供給し、それぞれの問いが対象側へ戻されていた。

これらは、**既存runtime能力が自然な実作業で再び現れたartifact evidence**として読める。

しかし、次は言えない。

- CSWが因果的にその構成を生んだ。
- 利用者がCSWの成功と評価した。
- 現行正本に役割分離型が欠けていた。
- 事例が複数あるからruntime規則を追加すべきである。

PR #146の「現行正本で最も暗黙なのは、複数体系を異なる役割で重ねてもよいという候補」という記述は、**当時の読みとして履歴に残すが、現在の判定としては採用しない**。

## 現行Routerへ戻す

現行 `ROUTER.md` の参照表は、

> 関係種別、欠落と接続、複数体系 → `methods/transformation.md`

と明示している。

また `src/manifest.json` では、`transformation.md` は `01-framework-and-kj.md` のknowledge groupに含まれ、`system-selection.md`、`framework-application.md`、`integration.md` と同じ主要方法群に置かれている。

したがって、複数体系能力がpackageから外れている、あるいは参照不能であるという静的欠落も確認できない。

一方、探索利用の読み込み順では、candidate recallから`framework-application.md`へ進む流れが文章として前景化し、**候補が複数立った場合に`transformation.md`へ進む条件は、参照表ほど逐次手順には前景化していない**。

これは静的な能力欠落ではなく、実行時に参照先へ到達する確率の問題かもしれない。

しかし、Routerがすでに「複数体系」の参照先を明示している以上、これも現時点では欠落と断定しない。

## OpenRouterによる回帰確認を試みた記録

2026-09-04、現行Routerだけを見たモデルが、複数体系を役割分離して使う課題で `transformation.md` を次の参照先として選ぶかを確認する小規模なfree-tier API試行を設計した。

目的はモデル性能の採点ではなく、**routing reachabilityの観測**である。

同一freeモデル、同一入力で少数回の実行を試みたが、実行環境のDNS名前解決に失敗し、OpenRouter APIへ到達する前に全試行が終了した。

したがって、この試行からモデル挙動についての観測値は得ていない。

- API応答なし。
- route選択結果なし。
- 成功／失敗判定なし。
- Issue #144の根拠には数えない。

利用者からは、OpenRouterの日次・週次・月次の無料枠を、研究・比較・回帰確認に意味がある場合は積極的に利用してよいという直接方針が示されている。今後ネットワークが利用できる実行環境では、無料枠の温存を理由にこの種の確認を避けない。ただしAPI出力は人間判断や測定真実へ昇格させない。

したがって、事例数を増やして欠落を強化するのではなく、**正本にある能力が実作業でも現れ得ることを示す匿名化されたartifact evidence**として置く。

### 島C――残るならrouting reachabilityである

CC-006、CC-007、CC-008、CC-009。

これはsourceに一文足せば必ず改善するとは限らない。プラットフォームごとのSkill reference読み込み、モデルの参照選択、課題の表現なども関わる。

したがって、現時点ではsource変更ではなく自然実行時の観測対象へ戻す。

## Issue #144の再基準化

Issue #144を、

> 複数体系compositionの静的能力が欠けている

というIssueとしては扱わない。

現行の問いは次の一つへ縮小する。

> **candidate recallで複数の構造型が候補へ上がった自然な実作業で、既存の`transformation.md`が必要時に前景化され、各体系へ異なる情報種別を担当させる操作まで実行されるか。**

観察するのは、たとえば次である。

- 複数体系を代替候補として並べるだけで終わらないか。
- 二つ目以降へ一つ目では扱えない情報種別を担当させるか。
- 独立した軸・役割を保ったまま対象へ返せるか。
- 一対一対応や確証の重複へ滑らないか。
- 必要な場合に`transformation`相当の操作が自然に現れるか。

これらが自然な実作業で問題なく現れるなら、Issue #144は追加runtime変更なしで閉じられる。

逆に、Routerの参照表があるにもかかわらず反復して`transformation`へ到達しない場合だけ、最小のrouting補足を検討する。

## 現在の判定

**静的なcomposition能力不足という判定は撤回する。**

現行正本は、複数体系の役割分離、直交重層、軸の独立性、異なる情報種別の担当、過剰確証の回避をすでに持っている。

PR #145/#146で得た研究材料は、方法の細部を読むための履歴として保存する。ただし現在の改善課題はそこから一段縮小し、**既存能力が実行時に必要な場面で呼び出されるか**だけを自然利用で観察する。

この訂正から新しいruntime規則は追加しない。
