# R3――runtime純化後の具体能力を機能単位で棚卸しする

作成日: 2026-09-01

## 目的

`2026-09-01-post-pr72-residual-map.md` で残したR3は、領域固有の技法をruntimeから外した後、その技法が担っていた具体的な能力をどこへ残せばよいか、という問題である。

ここで避けたいのは、二つの逆方向の誤りである。

1. runtimeから外したのだから、必要な能力もすべて不要だったとみなすこと。
2. 失うのが怖いという理由で、外した文書や技法を別の常設層へ丸ごと保存し直すこと。

後者を行うと、runtimeの純化で減らした複雑さを、別の名前の保管庫へ移しただけになる。

そのため、この棚卸しでは旧文書を単位にせず、**その文書が何を可能にしていたかという機能**を単位にして、現在のsourceと照合する。

## 処遇の区分

旧機能は、ひとまず次の五つに分けて考える。

1. **現コアへ吸収済み**
   - 現在のKJ、文化体系選定、変換、来歴、長期周回などに、より一般的な形で機能が残っている。
   - 旧技法を別に保存する必要はない。
2. **領域固有として外す**
   - 創作、文章表現、協働、UI、設計実務など、その領域の品質基準に属する。
   - CSWではなく、呼び出し側の文脈や領域スキルが担う。
3. **文化体系資料層へ置く候補**
   - 特定の文化体系や思想体系に固有の操作・観察軸であり、体系を薄めず再利用する価値がある。
   - runtime規則ではなく、その体系の資料として保持する方が自然である。
4. **別スキル・事例として再利用する候補**
   - 複数領域で繰り返し役立つが、CSWの二つの中核能力には属さない。
   - 実利用の反復が確認できた場合に、併用スキルや具体例として独立させる。
5. **履歴だけで十分**
   - 現在のコアで代替でき、独立した再利用需要も確認できない。
   - Git履歴や旧タグが保存しているだけで十分であり、現行の資料面へ複製しない。

この区分も固定分類ではない。後の実利用によって、処遇は変更できる。

# 1. `character-and-taiheki.md`

v0.2.0では、体癖を人物造形・描写・改稿の一貫性検査へ使う文書だった。

旧文書が担っていた主な機能は、次の三つに分けられる。

## 1.1 観察者が選んでいない身体的な軸を供給する

たとえば、姿勢、重心、疲労、食欲、緊張・弛緩時の反応など、心理説明だけでは抜けやすい観察軸を外部類型から得る。

### 現在

`domains/human-and-taiheki.md` に、ほぼ同じ核が残っている。

現在は人物造形の技法としてではなく、**人間観察の次元を増やす限定的な外部体系**として位置づけられ、観察可能な身体反応と対象固有の例外へ戻して検証する形になっている。

### 処遇

**現行のdomain層へ吸収済み。**

この機能を、旧人物造形文書として別に保存する必要はない。

## 1.2 第1項／第2項によって、表層と不随意な反応の差を見る

### 現在

これも `human-and-taiheki.md` に、仮説的な比較軸として残っている。

### 処遇

**現行のdomain層へ吸収済み。**

## 1.3 人物造形・描写・改稿へ直接使う

人物を描写した後に型を確定する、詳しく描写する人物だけへ適用する、といった運用は、創作実務に属する。

### 処遇

**領域固有として外す。**

現在のCSWが人物造形の技法を直接持たないことは、能力喪失とはみなさない。必要であれば、創作側の文脈や別スキルが担う。

# 2. `creative-patterns.md`

旧 `creative-patterns.md` は、経験、反復、時間、深層、笑い、感情、連作、異分野語彙による再記述など、性質の異なる多くの補助パターンを一つの文書へ集めていた。

この文書は、R3を考えるうえで重要である。削除された文書名だけを見ると、大きな能力群が失われたように見えるが、機能単位で見ると処遇が異なる。

## 2.1 時間構造――蓄積、回帰、周期、段階変化

### 現在

`methods/system-selection.md` は時間モデルと遷移モデルを持ち、周期、蓄積、回帰、段階変化、到達しない状態、戻らない状態などを探索できる。

`methods/transformation.md` も、時間的推移を独立した関係種別として対象へ戻して検証する。

### 処遇

**現コアへ吸収済み。**

創作専用の「時間の質」という旧包装を保存しなくても、一般化された機能は残っている。

## 2.2 深さの異なる層を分け、別体系で見て統合する

旧文書には、個人の身体、場所や物に蓄積した共有経験、局所と全体に反復する同型構造を分け、層ごとに別の体系を使う考えがあった。

### 現在

`methods/transformation.md` に、この構造がほぼ直接残っている。さらに、直交する体系を重ねて、単独体系からは出ない交点を得ることも明示されている。

### 処遇

**現コアへ吸収済み。**

## 2.3 経験への変換

身体・感覚、認知、行動・関係、環境・構成へ分散して表現するという旧手法は、具体的な表現設計として強い。

### 現在

CSWの現在の中核は、文化体系の構造を対象専用の質問、検査、手順へ変換するところまでを担う。どの表現経路へ落とすかは、成果物の領域によって異なる。

### 処遇

**領域固有として外す。**

ただし、執筆以外の領域でも同じ四経路が繰り返し必要になる実例が集まった場合は、別スキルや事例として再検討できる。

## 2.4 反復と明示度、笑い、感情、連作

これらは、いずれも創作や表現設計に強く依存する。

- 反復するたびに関係や機能を変える。
- 潜在／示唆／明示の度合いを調整する。
- 笑いの機構や倫理的帰結を見る。
- 感情を発生機構・効果・配置で扱う。
- 連作で記憶減衰を見込み、情報を再導入する。

### 処遇

**領域固有として外す。**

これらをCSWへ戻すと、文化体系探索とKJ統合のスキルが、創作技法集へ再び広がる。

## 2.5 既存機能への統合

旧文書には、新しい要素を追加する前に、既存の文、行動、会話、機能、手順へ追加の役割を統合できないか確認する、という操作があった。

これは創作だけに限らず、設計、文書、UI、業務手順などでも成立し得る。

一方で、この操作は文化体系探索やKJ統合に固有ではない。一般的な設計・編集上の節度とも読める。

### 処遇

**別スキル・事例として再利用する候補。ただし現時点では研究残差。**

この機能が、複数領域の人的利用で繰り返し明示的に必要とされるかを確認する。反復がなければ、Git履歴に残すだけでよい。

## 2.6 異分野の語彙による再記述

旧文書では、別の根拠で成立している主張へ、異分野の語彙から別の理解経路を追加する操作があった。

現在のCSWにも、外部体系から異なる見方を供給し、対象へ戻す機能はある。しかし、受け手ごとに理解経路を設計するところまでをCSWの責務とはしていない。

### 処遇

**原則として領域固有の出力設計。**

ただし、異分野語彙を使うこと自体が探索段階の問い生成に働く場合は、現在の探索利用で扱える。受け手向けの言い換えとして独立保存する必要は、現時点では確認できない。

旧文書は、成果物の明示度、受け手別の導入経路、協働者への引継ぎを扱っていた。

## 3.1 体系の関係を、対象で使える形へ変換する

### 現在

`methods/transformation.md` が、体系内の関係を対象専用の動詞、質問、検査項目、手順へ変換する役割を担っている。

### 処遇

**現コアへ吸収済み。**

## 3.2 反証条件、停止理由、未確定事項、再開条件を残す

### 現在

`core/iteration.md` と `governance/governance-and-records.md` が、残差、再開条件、反証条件、判断来歴、採用・撤回を扱う。

### 処遇

**現コアへ吸収済み。**

## 3.3 受け手別の明示度、低負荷の導入、複数の導入経路

### 現在

現在のCSWは、成果物を誰にどの順序でどう見せるかという一般的な出力設計を責務にしていない。

### 処遇

**領域固有として外す。**

これは文書作成、プレゼンテーション、UX、教育、協働など、呼び出し側の品質基準に属する。

## 3.4 協働者への引継ぎ

分析の到達点、停止理由、分岐案、既定の進め方などを協働者へ渡す操作も、一般的な作業管理・協働設計に近い。

CSW内で必要なのは、判断の来歴や未解決事項を失わないところまでであり、引継ぎ成果物の設計そのものではない。

### 処遇

**領域固有として外す。**

# 4. R3から見える現在の結論

今回確認した三文書については、「runtime純化によって重要能力が大きく失われた」という一括した結論は支持されない。

むしろ、次のように読める。

1. **一般化できる認知機能の多くは、現在のコアへ吸収されている。**
   - 身体的な観察軸の供給。
   - 時間・遷移モデル。
   - 深さの異なる層の分離。
   - 複数体系の交差。
   - 対象専用の質問・検査・手順への変換。
   - 反証条件、残差、再開条件、採用・撤回の来歴。
2. **創作・出力・協働に固有の技法は、意図的に外した方が現在のスキル境界と整合する。**
3. **旧文書を丸ごと保存する新しい常設層は、現時点では必要ない。**
   - v0.2.0タグとGit履歴が、過去の具体記述をすでに保存している。
   - 現行の資料面へ複製すると、どれが現在推奨される能力なのか分かりにくくなる。
4. **独立して再検討する価値が残る機能は少数である。**
   - 現時点では「既存機能への統合」が最も明確な候補である。
   - ただし、CSW固有の能力とはまだ言えない。

したがって、R3は「能力保管庫を新設する」というアーキテクチャ問題から、**削除された機能を、その後の実利用に応じて適切な層へ処遇する問題**へ縮小できる。

# 5. 今後の処遇ルールを固定規則にしない

今回使った五区分は、研究上の整理には有用である。

しかし、これを直ちに新しい保守規則へ昇格させない。

将来、別の機能をruntimeから外すたびに詳細な「能力処遇票」を必須にすると、それ自体が保守負荷になる可能性がある。

まずは、実際に「外したために必要な能力へ戻れなくなった」という事例が生じるかを見る。

そのような事例が反復する場合に初めて、削除時の機能処遇を保守プロセスとして定式化する。

現段階では、この研究記録とGit履歴を、R3の再開点として残せば十分である。

# 6. R3の残差

今回の棚卸し後、R3で前景に残す問いは次の二つまで縮小する。

## R3-A――既存機能への統合は、CSW外でも再利用すべき横断能力か

新しい要素を増やす前に、既存の文、行動、機能、手順へ役割を統合する操作は、複数領域で成立し得る。

ただし、一般的な設計・編集原則でもあるため、CSWへ戻す理由はない。

人的利用で繰り返し明示されるかを観察し、必要なら併用スキルや事例として扱う。

## R3-B――削除された具体技法へ戻れない実害が本当に起きるか

「再生成できないかもしれない」という可能性だけでは、新しい保存層を正当化しない。

実案件で、過去版にあった具体技法が必要になり、現在のコア、領域側の方法、Git履歴の参照だけでは十分に回復できなかった事例が生じるかを確認する。

その事例が現れるまでは、R3を静的アーキテクチャへ拡大しない。
