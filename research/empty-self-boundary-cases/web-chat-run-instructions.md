# Web Chatで境界ケースを実行する手順

## 目的

この文書は、`research/empty-self-boundary-cases/` のケースをWeb Chatで実行するとき、何をモデルへ見せ、どの段階で追加指示を与えたかを後から追えるようにするための手順である。

完全な再現実験は目指さない。Web Chatでは、モデル更新、会話履歴、製品機能、内部routingなどを完全には固定できないためである。

通常は自然な実作業を優先する。境界ケースは、自然利用だけでは切り分けにくい具体的な問いが生じた場合に、必要な範囲だけ使う。

## 事前準備

比較条件を分ける場合は、一つの条件につき新しいチャットを使う。

同じチャットで条件Aの出力を見た後、そのまま条件Bを実行しない。前の出力や会話内の修正が次の条件へ残るためである。

生成側へ次を渡さない。

- このディレクトリのREADME。
- 対象ケースの `reference.md`。
- `run-record-template.md`。
- この実行手順。
- API実行手順。
- ケースの狙いを説明する研究文書。

これらには、後から検証したい境界が書かれている。

モデル表示、製品モード、利用したtoolなど、後で解釈に必要な環境情報は記録してよい。

## 共通の最初の依頼

ケースを実行する場合、必要以上に検査の狙いを説明しない。

たとえば次の程度にとどめる。

```text
これから一つのケースを扱います。
提示する input.md の材料と作業要求に従って作業してください。
元材料と、あなたが新しく考えたことは区別できる形にしてください。
```

「このケースでは因果の追加を避けてください」のように、検査したい答えを先に教えない。

## 条件A――現行CSWを通常どおり使う

比較を行う場合の基準線である。

### 与えるもの

1. 対象ケースの `input.md`。
2. その課題を現在のCSWで扱うなら、本来読む現行文書。

現行Routerから自然に到達する文書を使う。

PR #85以降は、CSWを使うラウンドでは `core/cognitive-stance.md` を含むことも通常利用の一部である。追加promptを有利に見せるため、現行正本にすでにある原則を基準線から意図的に外さない。

たとえば、

- カード化・束ね・表札が中心なら `methods/integration.md`。
- 文化体系の用途判断なら `methods/system-selection.md` や `methods/framework-application.md`。
- 関係種別、欠落と接続、複数体系なら `methods/transformation.md`。
- 委任範囲や上位原則が関係するなら `core/principles-and-constraints.md`。

など、通常の利用時と同じ判断で参照する。

### 与えないもの

- `reference.md`。
- 旧試作prompt。
- 境界例。
- ケースの狙いを説明する資料。

出力後、そのチャット内でモデル自身へ総合的な自己採点を依頼しない。

## 条件B――認知姿勢を局所的に再提示する

**必要な問いがある場合だけ使う。**

たとえば、長い作業の途中で `cognitive-stance` が失われるように見え、局所的な再提示が必要かを切り分けたい場合である。

条件Aと同じ現行文書を使い、比較したい認知核だけを追加する。

追加した文章そのものをrun recordへ残し、他の条件を不用意に変えない。

## 条件C――工程別指示を追加する

**同型の歪みが特定工程で反復する場合だけ使う。**

条件Bまたは現行正本に加えて、そのケースで実際に使う工程の指示だけを追加する。

どの指示を足すかは、ケースの正解を知っているからではなく、実際にどの工程で切り分けが必要になったかから決める。

`reference.md` を読んだ後に条件Cを設計する場合は、その内容を答えとしてpromptへ逆輸入しない。追加した指示と、その選択理由を記録する。

## 条件D――境界例を追加する

**抽象的な原則や工程別指示だけでは、同型の意味損失を切り分けにくい場合だけ使う。**

例を使う場合は、対象固有の答えを教えるのではなく、どこで元材料と新しい意味の来歴が混ざるかを示す。

たとえば、

```text
元材料:
何か気になる。しかし、なぜ気になるのかはまだ分からない。

材料の未確定性を残した例:
理由はまだ言えないが、この箇所に注意が戻ってくる。

対象を上書きした例:
説明できない不安があり、潜在的な危険を直感的に察知している。
```

のように、後者で何が新たに足されたかを区別できる形にする。

条件Dも新しいチャットで実行する。前のチャットの修正履歴と、境界例の効果を混ぜない。

## A〜Dを全部回す必要はない

現在のA〜Dは固定ベンチマークではない。

- 現行CSWで問題が見えなければAだけで終えてよい。
- 再提示の要否だけを見たいならAとBだけでよい。
- 工程別の問題がすでに特定されているなら、必要な条件だけを設計してよい。

比較条件を増やすこと自体を成果にしない。

## 出力後の検証

生成が終わったら、その条件のチャットで追加生成を止める。

その後で `reference.md` を開き、`run-record-template.md` に沿って元材料へ戻る。

検証で見るのは、モデルが「私は対象を尊重しました」と説明できるかではない。

具体的に、

- どの語や出来事が元材料から来たか。
- どの因果や一般化を新しく足したか。
- どの未確定性を残したか。
- 何を判断し、何を保留したか。
- 新しい仮説をどの来歴に置いたか。
- 必要なreferenceへ到達したか。

を追う。

## 条件間比較

一つの順位へまとめない。

たとえば、

- 再提示すると意味の追加は減ったが、仮説形成まで弱くなった。
- 工程別指示を加えると、仮説を元材料とは別の来歴に置けるようになった。
- 境界例を加えると差は守られたが、例の言い回しを表面的に模倣した。
- 同じ現行CSWでも、製品モードを変えるとreferenceの参照行動が変わった。

という形で、何が変わったかを分けて記録する。

文章量、丁寧さ、構造化の程度だけで、対象への忠実性や方法の有効性を判断しない。

## APIと比較する場合

Web ChatとOpenRouter APIを比較する場合は、`openrouter-free-tier-run-instructions.md` も参照する。

Web ChatとAPIでは、モデル名が似ていてもsystem layer、tool、routing、contextの扱いが同じとは限らない。

したがって、差が出た場合もすぐ「APIだから」「Web Chatだから」と因果化しない。少なくとも、

- モデル。
- 入力した文書。
- system / user messageの構成。
- toolの有無。
- 会話履歴。
- providerやrouting。

を分けて読む。

## 正本へ進む前に

一つのケースや一回の比較で差が出ても、そのまま `src/` へ追加しない。

まず、

1. 現行正本だけでは本当に足りないか。
2. 別種の自然な実作業でも同じ問題があるか。
3. モデルや製品モード固有ではないか。
4. source不足ではなくroutingや読み込み順の問題ではないか。
5. 指示を追加すると逆方向の歪みが出ないか。
6. 常時核でなければ働かないのか、工程別または局所再提示で十分か。

へ戻る。

この検査は、追加規則を作るためではなく、**本当にどこに差があるのかを切り分けるため**に使う。
