# 「己を空しくする」プロンプトの境界ケース検証

## 目的

このディレクトリは、KJ法の「己を空しくしてデータをして語らしめる」という姿勢を生成AIへ伝える実験用プロンプトについて、実際にどのような読みの差が生じるかを確認するための研究用ケース集である。

ここでは、プロンプトを「よい文章を出すための工夫」として評価しない。

見たいのは、生成AIが自分の語彙、理論、説明力、善悪判断、過去の規則、役割観を対象より先に置かず、**対象によって自分の読みを変えられるか**である。

そのため、検証は生成AI自身の自己評価ではなく、元材料と、後から利用者が実際に与えた補正へ戻って行う。

## このケース集の位置づけ

このケース集はWeb Chat Living Labのprospectiveな実作業記録ではない。

過去に人的補正が起きた案件から、生成AIが意味を先回りしやすい境界を取り出して再構成した、**retrospectiveなプロンプト境界検査**である。

したがって、ケース数や成功率をCSWの効果指標にしない。ここで見つかった差も、そのまま因果効果とはみなさない。

目的は、正本へ何を入れるかを急いで決めることではなく、

- どの指示が対象固有の差を守るのか。
- どの指示が過剰な自制を生むのか。
- どこまでを常時核へ置くべきか。
- どこからを工程別の補助指示にするべきか。
- 対比例を使うなら、どの失敗境界に限るべきか。

を、元材料へ戻りながら見極めることである。

## 入力と参照を分ける

各ケースは、`input.md` と `reference.md` に分ける。

### `input.md`

生成時にモデルへ見せる材料である。

後から利用者が与えた補正、望ましい結論、後続の成功・失敗評価は入れない。できるだけ、補正が必要になった時点の材料と作業要求だけを残す。

### `reference.md`

生成後の検証でだけ読む。

主に次を残す。

- 利用者が後から直接述べた補正。
- その補正によって、何が失われるのを防ごうとしていたか。
- 元材料へ戻って確認できる境界。
- 生成AIが後から付けた評価とは区別すべき事項。

`reference.md` は正解集ではない。

利用者の補正も、その案件で生じた具体的な判断であり、別の案件へそのまま一般化してよいとは限らない。検証では、出力が補正文と同じ言葉を使ったかではなく、**同じ種類の意味損失を起こしていないか**を見る。

## 比較条件

同じケースを、できれば新しいWebチャットで別々に実行する。

### 条件A――現行KJのみ

現行 `src/ja-JP/methods/integration.md` を使う。

「己を空しくする」試作プロンプトは追加しない。

### 条件B――常時核を追加

条件Aに加え、`research/human-use-gap-kj/2026-09-01-empty-self-prompt-prototype.md` の「常時核――役割と成功条件」だけを与える。

ここでは、工程ごとの細かな注意はまだ加えない。

### 条件C――必要な工程別指示を追加

条件Bに加え、そのケースで実際に使う工程の指示だけを与える。

たとえば、カード化のケースならカード化、束ねのケースなら束ねと表札だけを使う。全文を毎回読み込ませることを既定にしない。

### 条件D――境界例を追加

A〜Cで同型の意味損失が残る場合だけ、良い例と悪い例の対照を加える。

最初からDを使わない。例の文体や表面構造を模倣しただけなのか、原則を理解して境界を守ったのかを分けにくくなるためである。

## 実行時の依頼

各条件では、ケースの `input.md` に書かれた作業要求をそのまま使う。

必要以上に「この実験では○○が重要です」と補足しない。補足自体が答えを教える可能性がある。

モデルや製品モードなど、後から比較に必要な環境情報は記録してよい。ただし、条件をそろえるために実作業を不自然に縛らない。

## 検証の順序

出力を得た後で初めて `reference.md` を開く。

次の順で確認する。

1. **元材料へ戻る**
   - 元にない因果を足していないか。
   - 元にない人物の内面を作っていないか。
   - 元より一般化していないか。
   - 評価の向きを変えていないか。
   - 確度を上げ下げしていないか。
2. **そのケース固有の境界を見る**
   - 理由未確定の注意を説明へ変えたか。
   - 局面固有の節度を普遍則へ変えたか。
   - 委任された判断をAI自身の役割観で縮めたか。
   - 方法上の美しさを、作品の人物・因果・事実より優先したか。
3. **利用者の直接補正と照らす**
   - 同じ補正が再び必要になりそうか。
   - 補正文と同じ言葉を使ったかではなく、その補正が守ろうとした差が残っているかを見る。
4. **逆方向の歪みを見る**
   - 慎重さが強すぎて、材料から十分に言えることまで判断しなくなっていないか。
   - 仮説形成や構造発見まで弱くなっていないか。
   - 「己を空しくする」を、自己否定や責任回避へ変えていないか。

## 記録方法

総合点は付けない。

条件ごとに、次のような自然言語の観察記録を残す。

- どの材料をそのまま保持したか。
- どこで材料にない意味を足したか。
- 何を保留したか。
- 何を判断したか。
- 条件を変えると、どの箇所が変わったか。
- 変化が対象への忠実性に関係するのか、単なる文章量・文体差なのか。
- 利用者の直接補正へ戻したとき、どの差が重要に見えるか。

観察者が生成AIの場合は、その判断もAIによる解釈として扱う。可能な限り元材料の具体的な差分を併記する。

## 最初の四ケース

1. `case-01-unexplained-attention/`
   - 理由の分からない「何か気になる」を、もっともらしい原因へ変えないか。
2. `case-02-contextual-framework-use/`
   - 一局面の節度を、文化体系利用の普遍的禁止則へ変えないか。
3. `case-03-delegated-authority/`
   - AI自身が安全だと思う役割像を、人間から委任された判断範囲より優先しないか。
4. `case-04-work-life-over-method/`
   - 不可視性、余白、抑制などの方法上の美しさが、作品の人物、因果、事実、作者の選択を覆わないか。

## 正本化までの距離

このケース集の結果だけで `src/` を変更しない。

少なくとも、

- 異なる種類のケースで同じ核が働くこと。
- その核が過剰な自制を生まないこと。
- 実案件の `natural_work` でも、同型の人的補正が減るか、対象固有の差が保たれること。
- プロンプトを常時核、工程別指示、事例のどこへ置くのが適切かが見えてくること。

を確認したうえで、正本への反映を検討する。
