# 「己を空しくする」認知姿勢の境界ケース

## 目的

このディレクトリは、KJ法の「己を空しくしてデータをして語らしめる」という姿勢について、生成AIの実際の読み方にどのような差が現れるかを確かめるための研究用ケース集である。

ここでいう「己を空しくする」は、知識や推論を捨てることではない。

> **自分の知識や推論を、対象によって修正され得る位置へ置く。**

という現在の認知核を、自然な実作業だけでは切り分けにくい場合に調べる。

よい文章を出したか、慎重な回答になったか、といった総合点では評価しない。元材料へ戻り、

- 対象固有の差が保たれたか。
- 新しい問いや仮説が、元材料とは別の来歴に置かれたか。
- AIの説明力や既存理論が対象を先回りしていないか。
- 反対に、慎重さが判断回避や仮説抑制へ変形していないか。

を見る。

## このケース集の位置づけ

このケース集は、Web Chat Living Labの `natural_work` を前向きに観測した記録ではない。

過去に人的補正が起きた案件から、生成AIが意味を先回りしやすい境界を取り出して再構成した、**過去事例に基づく診断・回帰確認用の研究資産**である。

したがって、

- ケース数。
- 実行回数。
- 成功率。
- 総合点。
- API利用量。

をCSWの効果指標にしない。

一つのケースで差が出ても、それだけでprompt、model、CSWの因果効果とはみなさない。

## いつ使うか

通常は、自然な創作、調査、設計、KJ統合を優先する。

このケース集は、たとえば次のような具体的な問いが生じた場合に必要な範囲だけ使う。

- 現行 `cognitive-stance` を読んでも同型の意味上書きが反復する。
- 長い作業の途中で認知姿勢が失われるように見える。
- 抽象的な原則だけでなく、工程別指示や対比例が必要かを切り分けたい。
- 慎重さが強すぎて判断や仮説形成が弱くなる。
- 現行Routerが案内しているreferenceへ、モデルが実行時に到達するか確認したい。
- release前に、重要な方法変更の限定的な回帰確認が必要になった。

問いがないのにケースを回すこと自体を研究成果にしない。

## 生成側へ見せるものを限定する

このディレクトリ全体を生成側へ渡してはならない。

README、`reference.md`、`run-record-template.md`、各実行手順には、検証したい境界や後から得られた知識が含まれている。

生成側へ見せてよいのは、原則として次だけである。

1. 対象ケースの `input.md`。
2. その課題を現在のCSWで通常どおり扱うなら、本来読む文書。
3. 比較条件として追加すると事前に決めた指示。

ケースの狙い、後から利用者が入れた補正、検証項目は、出力が終わるまで生成側へ伝えない。

## 入力と検証用参照を分ける

各ケースは `input.md` と `reference.md` に分かれている。

### `input.md`

生成時にモデルへ見せる材料である。

後から利用者が与えた補正、望ましい結論、成功・失敗評価は入れない。できるだけ、補正が必要になった時点の材料と作業要求だけを残す。

### `reference.md`

生成後の検証で初めて読む。

主に次を残す。

- 利用者が後から直接述べた補正。
- その補正によって、何が失われるのを防ごうとしていたか。
- 元材料へ戻って確認できる境界。
- 生成AI自身の後付け評価とは区別すべき事項。

`reference.md` は正解集ではない。

補正文と同じ言葉を出したかではなく、**同じ種類の意味損失が起きていないか**を見る。

## 基準線

比較する場合、最初の基準線は**その時点の現行CSWを通常どおり使った状態**である。

PR #85以降は、Routerの読み込み順に従い、CSWを使うラウンドでは `core/cognitive-stance.md` を含むことも基準線の一部になる。

新しいpromptや補助規則を有利に見せるため、現行正本にすでにある原則を意図的に抜かない。

## 比較条件

旧研究ではA〜Dの条件を使った。現在も必要な切り分けに応じて再利用できるが、**すべてのケースをA〜Dまで機械的に回さない**。

### 条件A――現行CSW

その時点の通常のCSWだけを使う。

### 条件B――認知姿勢の再提示

長い作業で認知姿勢が失われるかを見たい場合などに、必要な核だけを局所的に再提示する。

### 条件C――工程別指示

同型の歪みが特定工程で反復した場合だけ、その工程の指示を加える。

### 条件D――境界例

抽象指示だけでは差を切り分けにくい場合だけ、対象の差を守った例と、対象を上書きした例の対照を加える。

比較したい意味差以外の条件は、できるだけ保つ。

## 実行面

### Web Chat

`web-chat-run-instructions.md` を参照する。

Web Chatではモデル更新、会話履歴、製品機能などを完全には固定できない。完全再現ではなく、何を見せ、何を追加したかを追える状態を作る。

### OpenRouter free-tier API

`openrouter-free-tier-run-instructions.md` を参照する。

利用者の直接方針により、日次・週次・月次の無料枠は、研究上の問いが明確な場合には積極的に利用してよい。

ただし、

- paid fallbackを使わない。
- APIキーを研究記録やsourceへ残さない。
- free modelの可用性やrate limitを外部条件として扱う。
- raw outputと後からの解釈を分ける。
- API出力やLLM自己評価を人間判断や測定真実へ昇格しない。

という境界を保つ。

## 実行後の検証

出力を得た後で初めて `reference.md` を開く。

`run-record-template.md` に沿って、次の順で元材料へ戻る。

1. **元材料として保持されたもの**
   - 主体、出来事、証拠状態、両義性、未確定性、反例などが残ったか。
2. **新しく生じた意味**
   - 問い、仮説、関係、表札などが、元材料とは別の来歴に置かれているか。
3. **来歴を失った混入**
   - 元にない因果、内面、一般化、評価方向、確度変更を、元材料に最初からあった意味として扱っていないか。
4. **ケース固有の境界**
   - 利用者の直接補正が守ろうとしていた差が残っているか。
5. **逆方向の歪み**
   - 慎重さが判断回避、責任回避、仮説抑制へ変わっていないか。

## 条件間比較

一つの順位へまとめない。

たとえば、

- 意味の追加は減ったが、仮説形成まで弱くなった。
- 仮説の量は変わらないが、元材料との来歴が明確になった。
- 必要なreferenceへ到達したが、別の体系を過剰に対応付けた。
- モデルを変えると判断量は増えたが、未確定性の扱いも変わった。

という形で、**何が変わったかを分けて記録する**。

文章量、丁寧さ、構造化の程度だけで、対象への忠実性や方法の有効性を判断しない。

## 最初の四ケース

生成側から狙いを見えなくするため、パスは番号だけにしている。

- `case-01/`
- `case-02/`
- `case-03/`
- `case-04/`

各ケースが何を検証するために作られたかは、そのケースの `reference.md` に記録している。

## 正本へ反映するまでの距離

境界ケースやAPI比較の結果だけで `src/` を変更しない。

少なくとも、

- 自然な実作業でも同型の問題が確認できるか。
- 別種のケースでも同じ機能が必要か。
- モデル固有の差ではないか。
- 現行正本にすでに同じ能力がないか。
- routingや読み込み順の問題ではないか。
- 追加指示が逆方向の歪みを生まないか。

を確認する。

正本への反映を急ぐのではなく、**切り分けに必要な追加材料を得るための資産**として使う。
