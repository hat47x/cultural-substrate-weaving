# 文化体系の置き場所と採否状態の混線を監査する

## 対象

`methods/framework-application.md` の次の箇所を監査する。

> 必要に応じて、成果物への反映、内部足場、補助模型、不採用、歪み検出を分ける。

現行見出しは「採用状態と過剰適用」であり、この5項目が一つの状態軸であるように読める。

今回の問いは、5項目を単に非網羅化することではない。**体系が実作業のどこに残ったか**と、**体系についてどのような採否・歪み判断が行われたか**が同じ軸へ混ざっていないかを確認する。

## 現行runtime内の二つの語彙

### `framework-application.md`

一列に次を置く。

- 成果物への反映
- 内部足場
- 補助模型
- 不採用
- 歪み検出

前半三つは、体系または体系から得た構造が**どこに・どの形で残ったか**を表す。

後半二つは、体系利用についての**判断・評価状態**を表す。

### `governance/governance-and-records.md`

判断来歴として別に次を持つ。

- `採否：adopted / backgrounded / rejected / distorting / reopened`

さらに現行`evaluation.md`は、採否について「判断主体と根拠を残す」としている。

したがって現行repo内でも、成果物上の残り方と採否判断は完全には同じ概念として扱われていない。

## 系譜

### 1. `2b39432…` — 4状態を導入

`2b39432ae98fd0fae6a5f2a000dea1138850dd5f` は、外部レビューを既存ルールと照合しながら取り込んだ変更である。

同コミットは「adopted frameworkがlandする四状態」を追加し、実際の文言として次を置いた。

- 成果物への反映
- 内部足場
- 補助模型
- 不採用

当時のgovernanceも「体系の採用状態（反映、内部足場、補助模型、不採用）」として同じ4語を判断記録へ載せていた。

この時点では、**残り方と体系妥当性を一つの状態として扱っていた**。

### 2. `d2b735d…` — 一軸化の欠陥を実測

`d2b735dc0abf79d22e743790e225fce09fac0cb1` は、実行結果からこの4状態の欠陥を明示した。

コミット記録では、4状態が「framework's validity」と「how much it produced」を折り畳んでおり、**棄却された体系が所見を産んだ場合に置けない**と指摘している。

実際に、

- 第一候補として棄却された体系が3つの生存所見を産んだ
- controlとして持ち込んだ体系が5つの生存所見を産んだ

という例が出た。

その結果、runtimeには次が明示された。

- 不採用は所見の取り消しではない
- 棄却された体系が産んだ生存所見も残り得る
- 体系の妥当性と産んだ件数を同じものにしない

これは、体系の採否と成果物への残存が**直交し得る**ことを実測したものと読める。

### 3. v40 `3dc8777…` — governanceでは採否語彙を分離

`3dc8777491977dd58ab506249a30306769011fbc` はv40 production semantics統合で、governance側の判断来歴を次へ変更した。

- `adopted / backgrounded / rejected / distorting / reopened`

この語彙は「どこに残ったか」より、体系利用についての採否・継続状態を記録するためのものになっている。

一方、`framework-application.md`では、旧4項目に`歪み検出`を加えて、

- 成果物への反映
- 内部足場
- 補助模型
- 不採用
- 歪み検出

を一列に置いた。

つまりv40はgovernance側では二軸分離へ進んだ一方、method側の一文には**置き場所と採否判断の混在を残した**。

### 4. v0.5.0 — 決定権は外部条件・委任へ戻った

現行runtimeでは、採否そのものをSkillが自律決定する設計から離れ、判断主体と根拠を来歴として残す方向へ再基準化されている。

そのため、method側で「採用状態」という単一軸を固定するより、

1. 体系由来のものが実作業にどう残ったか
2. 体系利用について誰がどう判断したか

を分けて扱う方が、`state recording ≠ decision authority`にも整合する。

## 何を保持するか

今回の監査は、現行5概念を削る理由にはならない。

- **成果物への反映**：成果物に体系由来構造が現れる場合を記録できる。
- **内部足場**：成果物には現れないが分析を支えた場合を記録できる。
- **補助模型**：再利用可能な模型として残る場合を記録できる。
- **不採用**：体系自体を採用しない判断を記録できる。
- **歪み検出**：体系接触が対象を歪める方向へ働いたという観察・判断を記録できる。

問題は5概念の存在ではなく、**同じ一軸の相互排他的状態のように並べること**である。

特に`d2b735d…`の実例が示すように、`不採用`と`生存所見が成果物へ反映`は同時に成立し得る。

## runtime方針

`framework-application.md`では、少なくとも次の区別を明示するのが妥当である。

- **残り方・置き場所**：成果物への反映、内部足場、補助模型など。
- **採否・歪みについての判断**：不採用、歪み検出など。判断主体と根拠はgovernanceへ記録する。

ここで新しい固定taxonomyは作らない。前者も後者も必要に応じた代表例として扱う。

また、次を維持する。

- 不採用でも、そこから生じた問い・生存所見まで消さない。
- 採否と帰属状態を混同しない。
- `framework_generated / target_supported / cross_field_emergent / unresolved`は別の証拠来歴軸として保持する。
- Skill自身が採否を自律決定する規則へ戻さない。

## 結論

**5項目を一つの「採用状態」taxonomyとして開くのではなく、置き場所と採否判断を別軸へ戻す。**

根拠は単なる用語整理ではない。`d2b735d…`で、棄却された体系が複数の生存所見を産むという実例により、一軸状態では表現できないことがすでに確認されている。

v40 governanceの採否語彙と現行の判断主体・根拠記録を踏まえ、method側もその分離に合わせるのが次のruntime変更候補である。
